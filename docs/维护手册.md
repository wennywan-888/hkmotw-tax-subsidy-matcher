# 政策数据维护手册

写给未来的你。假设你已经忘了这套东西怎么用。

---

## 核心原则（先读这段）

> **机器负责发现变化，你负责确认发版。**

巡检脚本只会告诉你「这个页面变了」「这个金额对不上」，它**永远不会**自己改政策数据。
所有变更都必须你亲自打开官方原文核对、确认之后，才会写进正式数据。

这个设计是刻意的。政策类信息一旦出错，用户会拿着错的金额去申请，白跑一趟。
宁可慢一点，不要错。

---

## 两种维护方式

| | 云端（推荐） | 本地 |
|---|---|---|
| 谁触发巡检 | GitHub Actions 定时自动 | 你手动敲命令 |
| 在哪审批 | **手机上点 PR** | 终端里敲 a/r/u |
| 版本管理 | git 历史 | `data/versions/` 目录 |
| 回滚 | git revert | `confirm.py --rollback` |
| 适合 | 日常 | 临时核查某一条 |

**日常用云端**，本地留着应急和临时查单条。

# 第一部分 · 云端维护（日常）

## 你要做的只有一件事：审批 PR

Actions 会按下面频率自动巡检。发现变更时自动开一个 PR，GitHub 会推通知到你手机。

| 时间 | 巡检范围 | 为什么这个时间 |
|---|---|---|
| 每周一 09:00 | 申报窗口 | 唯一「错过就等一年」的东西 |
| 每月 1 日 09:00 | 全量 | 条款和额度常规体检 |
| 每季度末 28 日 | 链接有效性 | 政府网站改版频繁，链接会悄悄失效 |
| 1 月 2 日 | 全量 | 个税补贴 1/1 开放申报 |
| 3 月 15 日 | 申报窗口 | 个税补贴 3/31 截止，确认没变动 |
| 7 月 25 日 | 全量 | 前海十二条通常 7 月底发次年度指南 |
| 8 月 5 日 | 申报窗口 | 前海申报窗口 8 月开，只有两周 |

## 收到 PR 之后怎么处理

PR 正文里有一份**逐条核对清单**，每条都带：
- 数据表里现在写的值
- 巡检发现了什么
- **官方来源链接**
- 页面上抓到的原文片段
- 置信度

### 处理步骤

1. **点开官方链接，看原文**（这一步不能省）
2. 判断：

| 情况 | 怎么做 |
|---|---|
| 确实变了 | 在 PR 里直接编辑 `data/policies.json` 填正确值，把 `verification.status` 改回 `verified`，更新 `last_verified`，然后合并 |
| 是误报 | 从 `pending_items` 删掉对应那条，`status` 改回 `verified`，合并 |
| 暂时没空细看 | **也可以直接合并** —— 前台会显示「待核实」，比显示错误金额安全 |
| 完全不认可 | **关闭 PR**，正式数据一个字都不会变 |

3. 合并后 Actions 自动跑数据校验，通过即生效

> **为什么 PR 不直接填好新值让我一键合并？**
> 因为「变成了多少」需要读懂政策文件的上下文——分档表格、附件、口径说明。
> 让脚本猜，猜错就是把错误金额推上线。所以它只负责标「这条要看」，
> 具体数值由你填。这是刻意的取舍。

## 手动触发巡检

仓库页面 → **Actions** → 左侧选「政策巡检」→ 右上 **Run workflow**：
- `scope`：选 all / window / terms / links
- `only`：填 policy_id 就只查那一条（留空查全部）

手机上也能操作。

## 出问题时会怎样

巡检异常或被安全阀中止时，会**自动开一个 issue** 通知你，不会静默失败。

安全阀是刻意加的：政府站点通常有防护，云端定时任务无人看守，
连续 6 次抓取失败就中止、单次请求上限 80 次。宁可这次少查几条，也不要把 IP 打进黑名单。

**看到「巡检异常」issue 先别慌**，多数是政府站点临时限流，隔天重跑就好。

## 日常操作三步

### 第一步：跑巡检

```bash
py tools/patrol.py
```

跑完会告诉你发现了几条待处理项，报告存在 `reports/` 目录。全量跑一次约 1 分钟。

**只想查某一类：**

| 命令 | 检查什么 | 建议频率 |
|---|---|---|
| `py tools/patrol.py --scope window` | 申报窗口开闭 | **每周** |
| `py tools/patrol.py --scope terms` | 条款、补贴额度 | 每月 |
| `py tools/patrol.py --scope links` | 链接是否失效 | 每季度 |
| `py tools/patrol.py` | 全部 | 每月一次即可 |

**只查某一条政策**（最常用）：

```bash
py tools/patrol.py --only qh-employ-001
```

**限制请求量**（担心被限流时）：

```bash
py tools/patrol.py --max-requests 20
```

### 第二步：看报告

报告是 Markdown，直接双击 `reports/patrol-日期-时间.md` 就能读。

想在终端里快速扫一眼：

```bash
py tools/confirm.py --list
```

报告里每条都标了：
- **🔴 高** — 优先处理。链接失效、申报窗口变动都算这类
- **🟠 中** — 值得看。页面内容变了、额度对不上
- **🟡 低** — 大概率误报，扫一眼就行

还有**置信度**。`low` 的基本是脚本抽取逻辑不够聪明（比如页面用表格写分档金额），
不代表政策真变了。

### 第三步：确认变更

```bash
py tools/confirm.py
```

它会一条条问你。每条会显示来源链接——**先打开链接看官方原文，再做决定**。

| 选项 | 含义 | 什么时候用 |
|---|---|---|
| `a` 采纳 | 我核对过了，确实变了 | 官方原文确认变更 |
| `r` 驳回 | 误报 | 打开原文发现没变 |
| `u` 标记待核实 | 存疑 | 看不明白，先让前台显示「待核实」 |
| `s` 跳过 | 这轮不处理 | 没时间核，留到下次 |
| `q` 退出 | 放弃剩下全部 | 临时被打断 |

**全部驳回或跳过的话，数据一个字都不会变，也不会发新版本。**

选 `a` 之后它会问你具体改哪个字段、改成什么。字段路径用点号，例如：

```
benefit.amounts.bachelor          # 本科档补贴金额
application_window.start          # 申报开始日期
application_window.end            # 申报结束日期
application_window.actual_end_extended   # 实际延长到的日期
```

改完它会让你最后确认一次是否发布。确认后：
1. 当前版本自动备份到 `data/versions/`
2. `data/policies.json` 更新，版本号递增
3. `data/CHANGELOG.md` 自动追加变更记录

## 改错了怎么办

**云端**：找到那个 PR 的合并记录，点 Revert；或在 commit 页面点 Revert。

**本地**：

```bash
py tools/confirm.py --rollback
```

列出所有历史版本，选一个回滚。**回滚前会先把当前状态也备份一份**，
所以就算回滚错了也能再退回来。

看看有哪些版本：

```bash
py tools/confirm.py --versions
```

## 不用工具，直接手改

政策数据就是一个 JSON 文件，你完全可以直接编辑：

```bash
open -a "TextEdit" data/policies.json
```

改完**务必**校验格式，少一个逗号整个网站就打不开：

```bash
py -c "import json;json.load(open('data/policies.json'));print('格式正确')"
```

手改完记得同时更新两个地方：
1. 该条政策的 `verification.last_verified` 改成今天
2. `meta.data_version` 版本号 +1，`meta.data_as_of` 改成今天

> 顺便说：就算 JSON 真的改坏了，前台也不会白屏——
> `src/loader.js` 会自动加载 `data/versions/` 里最近的正常版本，
> 并在页面上提示「已加载备份版本」。
> 云端还有一道 PR 校验拦着，格式错了合并不进去。但你还是该尽快修好。

## 出问题怎么排查

### 巡检报了一堆「链接失效」

先用 curl 试一下真假：

```bash
curl -sS -o /dev/null -w "%{http_code}\n" https://那个网址
```

返回 `200` 说明链接是好的，是脚本抓取问题。
返回 `404` 说明页面真的没了，需要去官网重新找。

> 背景：部分深圳政府站点的 TLS 配置和 Python 内置 SSL 不兼容，会报 `BAD_ECPOINT`。
> 脚本已经改成优先用 curl 抓取、urllib 兜底，正常不会再误报。
> 如果又出现大面积误报，先检查 curl 是否还在：`which curl`

### 巡检脚本自己崩了

```bash
py tools/patrol.py --only 某个政策id
```

单条跑，看是哪条出问题。脚本的退出码有含义：

| 退出码 | 含义 |
|---|---|
| 0 | 正常 |
| 1 | 找不到数据文件 / --only 的 id 不存在 |
| 2 | policies.json 格式错误 |
| 3 | 巡检过程有异常 |
| 4 | 被安全阀中止（限流保护） |

### 报告里全是「额度疑似不一致」

大概率是脚本抽不到页面上的金额写法（表格、图片等）。
看置信度，`low` 的可以放心驳回。如果某条反复报，可以考虑：
- 换一个更好抓的来源 URL
- 或在该条 `verification.notes` 里记一句「金额以表格形式呈现，巡检易误报」

## 全年巡检日历

云端已按这个配好，本地手动跑也可以参照。

| 时间 | 做什么 | 为什么 |
|---|---|---|
| **每周一** | `--scope window` | 申报窗口是唯一「错过就等一年」的东西 |
| **每月 1 日** | 全量 `patrol.py` | 条款和额度的常规体检 |
| **1 月上旬** | 全量 + 重点查个税 | 个税补贴申报 1/1 开放、3/31 截止，**最要紧的窗口** |
| **3 月中旬** | `--scope window` 加密 | 个税申报即将截止，确认没变动 |
| **7 月下旬** | 全量 + 重点查前海 | 前海十二条通常 7 月底发布次年度指南 |
| **8 月上旬** | `--scope window` 加密 | 前海申报窗口通常 8 月开放，只有两周 |
| **10-11 月** | 全量 | 省级文件常在这个时段发布（47 号文就是 10/24） |
| **每季度末** | `--scope links` | 政府网站改版频繁，链接会悄悄失效 |

### 已知的关键时间点

- **前海十二条**：每年 8 月申报，窗口约两周（2025 年是 8/1-8/14，实际延到 8/18）
  政策本身有效期至 **2027-06-30**，届时需关注是否续期
- **大湾区个税补贴**：每年 **1/1 - 3/31**，受理上一纳税年度
  注意：申报前须先完成个税年度汇算清缴，而汇算清缴期是 3/1-6/30，
  **补贴 3/31 就截止了**，所以要提前办汇算
- **粤人社规〔2025〕47号**：有效期至 **2030-10-23**
- **福田英才荟指南**：有效期至 **2026-12-31**，按年度更新

## 文件都是干什么的

```
hkmo-subsidy/
├── data/
│   ├── policies.json      ← 政策数据，改政策只改这个
│   ├── schema.md          ← 字段说明书，加新政策前先看
│   ├── CHANGELOG.md       ← 变更历史
│   ├── 核实清单.md         ← 待核实事项，fact check 用
│   ├── snapshots/         ← 页面快照，用于比对差异（不用管）
│   └── versions/          ← 本地版本备份（云端用 git 历史，此目录不进 git）
├── src/
│   ├── matcher.js         ← 匹配引擎，不含任何政策内容
│   └── loader.js          ← 数据加载与失效兜底
├── tools/
│   ├── patrol.py          ← 巡检脚本
│   ├── propose.py         ← 生成 PR 提案（云端用）
│   └── confirm.py         ← 本地交互确认与发版
├── .github/workflows/
│   ├── patrol.yml         ← 定时巡检 + 自动开 PR
│   └── validate.yml       ← PR 合并前校验
├── reports/               ← 巡检报告
└── docs/
    └── 维护手册.md         ← 你正在看的这个
```

**要点：`src/` 里的代码不含任何政策金额和条件。** 政策全在 `data/policies.json`。
所以更新政策永远不需要改代码。

## 加一条新政策

1. 打开 `data/schema.md` 看字段规范
2. 复制 `policies.json` 里一条结构相近的，改内容
3. `verification.status` 先填 `"unverified"`
4. 核实清楚、拿到官方一手来源和原文引句后，再改成 `"verified"`
5. 校验格式：`py -c "import json;json.load(open('data/policies.json'))"`
6. 跑一次巡检建立快照：`py tools/patrol.py --only 新政策id`

**必填不能省的**（PR 校验会拦）：
- `sources` 至少一条 `is_primary: true` 的官方链接，且带 `quote` 原文引句
- `eligible_identities` 四类身份逐个标注（港永久 / 港非永久 / 澳永久 / 台）
- 拿不到官方依据的身份，标 `"unverified"`，**不要猜**
- 标 `verified` 的必须有 `last_verified` 日期

校验还会拦住不规范的港澳台表述，这是硬性要求。

## 最后一句

这套机制最容易失效的地方不是技术，是**你不看 PR 通知**。

所以内置了 180 天降级提示：超过半年没核实，页面会自己告诉用户
「本条信息已 X 天未核实，可能已过时」。这是替你向用户诚实。

但那只是底线，不是目标。云端已经把「每周跑巡检」自动化了，
你只需要在收到 PR 通知时花两分钟点开原文看一眼——
申报窗口是唯一错过就要再等一年的东西。
